AIエージェント連携型 語学学習プラットフォーム
プロダクト / システム設計ドキュメント v0.2
ChatGPT・Gemini等のAIエージェントを学習UIとして活用し、語彙・例文・復習履歴を独立した学習基盤に蓄積する
設計の中心思想
学習データの主権をAIエージェント側に置かない。ChatGPT、Gemini、将来の別エージェントは「会話・説明・出題」を担当する交換可能なクライアントとし、単語・表現・学習履歴・復習状態・ユーザー設定は本サービスが一元管理する。
1. 背景と目的
現在の生成AIは、語学学習において「分からない表現をその場で聞く」「自然な会話練習をする」「自分に合わせた例文やクイズを作る」といった用途に非常に向いている。一方で、会話中に得た学習事項を長期的・構造的に蓄積し、別のAIや別アプリから再利用する仕組みは弱い。
本プロジェクトでは、AIとの会話中に発生した学習事項を外部の学習基盤へ保存し、そのデータを任意のAIエージェントから参照・更新できる汎用的な語学学習サポートツールを構築する。
2. プロダクトビジョン
「どのAIと話しても、昨日までの自分の学習が続いている」状態を作る。
AIエージェントは先生・会話相手・出題者として利用する。
学習履歴はAIサービスから独立して永続化する。
ChatGPTからGeminiへ移っても、学習データと復習状態は引き継がれる。
専用Web/モバイルUIは「一覧・編集・復習・可視化」を補完する。
個人向けから開始し、将来的には学習サービスや教育事業者向けAPIにも展開可能な構造にする。

AIエージェントが担当

永続データの正本管理
意味・文法の説明
ユーザー別データ分離
会話練習
検索・重複管理

この境界により、生成モデルの性能は最大限利用しつつ、学習履歴の一貫性・可搬性・再現性はサービス側で担保できる。
12. 復習アルゴリズム
MVPではアルゴリズムを交換可能なStrategyとして実装する。最初から特定方式へ強く依存させない。
初期版: 習熟度 + 最終復習日時による簡易スケジューリング
次段階: SM-2系などの間隔反復
将来: 語彙難度、誤答傾向、回答速度、利用頻度、文脈依存度を加味した個別最適化
AIには「復習すべき項目の選定」まで委ねず、Review Engineが候補を返し、AIは出題形式や説明の仕方を最適化する役割に寄せる。
13. 重複・表記ゆれへの考え方
同一言語 + 正規化表記が一致しても、意味や品詞が異なる場合は別Senseとして保持可能にする。
大文字小文字、全半角、簡体字/繁体字等は検索用normalized_surfaceを別途保持する。
AIが登録前にsearchを行うことは推奨するが、最終的な重複防止はサービス側でも実施する。
既存項目への文脈追加と、新規項目作成を区別する。
14. セキュリティ / プライバシー
外部AIへ返すデータは要求された学習項目に限定する。
会話全文を無条件に保存しない。学習に必要な最小限の文脈へ要約・抽出する。
ユーザーは保存データを閲覧・修正・削除・エクスポートできる。
AIプラットフォームごとのトークン/APIキーはAdapter層またはSecrets管理へ分離する。
将来的な第三者提供を考慮し、user_idと外部サービスIDを直接同一視しない。
15. マルチエージェント対応
各AI向けに個別実装を増殖させないため、中心には共通のLearning Service APIを置く。AI固有処理は薄いAdapterに閉じ込める。
                   +-- ChatGPT MCP Adapter Learning Service <--+-- Gemini Adapter         API        <--+-- Custom Agent SDK                    +-- Web / Mobile Client  
Adapterは「AIがToolをどう発見・呼び出すか」の差分だけを吸収する。学習項目や復習という概念は共通ドメインのまま維持する。

20. 初期実装での推奨判断
最初の実装では、汎用性を意識しつつ抽象化しすぎないことを推奨する。中心データは LearningItem / LearningContext / ReviewEvent の3つに絞り、ChatGPTを最初のクライアントとして接続する。ただしインターフェース名やDBスキーマにはChatGPT固有語を入れない。
最初に証明すべき価値は「AIとの自然な会話の中で学習事項が勝手に散逸せず、あとから別の場所で復習できる」ことである。マルチAI対応は、この中心価値を壊さずにAdapter追加だけで実現できることを設計上保証する。

21. 学習プラン / ゴール管理
語学学習では、学習項目を蓄積するだけでは継続や達成感につながりにくい。そこで本サービスでは、一定期間の学習目的・重点領域・達成条件・学習ステップをまとめた「Learning Plan」を第一級のドメイン概念として扱う。
21.1 基本思想
学習開始時に、AIエージェントとユーザーが対話しながら現在地と短期ゴールを整理する。
ゴールは「日常会話ができる」のような広い目標だけでなく、「曜日を7つ言える」「自己紹介を3文で書ける」など、短期間で達成判定できる粒度まで分解する。
学習プランは固定カリキュラムではなく、その時点の気分・苦手・利用可能時間に合わせて作り直せる。
AIは計画案の生成・説明・調整を担当し、プラン・進捗・達成履歴の正本はLearning Service側で保持する。
「何を学んだか」だけでなく、「何を目指して、どこまで進んだか」をサービス全体で共有できるようにする。
21.2 プラン作成時の対話
新しい学習プランを開始するとき、AIエージェントは最低限次の観点をユーザーと確認し、Learning Plan案を生成する。
Current Level: 現在できること・できないこと。必要に応じて簡易チェック問題で推定する。
Goal: 今回の短期ゴール。例: 中国語で基本的な自己紹介ができる、曜日をすべて覚える。
Focus: vocabulary / grammar / pronunciation / listening / speaking / writing / reading などの重点配分。
Learning Style: 会話中心、クイズ中心、説明を読んでから実践、反復重視など。
Available Pace: 1回の学習時間、週あたりの日数、想定期間。
Mood / Preference: 今日は軽く復習したい、発音を重点的にやりたい、文章を書く練習をしたい等の一時的な希望。

21.4 Goal / Milestone / Step
Learning Planの下には、達成判定可能なGoal、途中到達点であるMilestone、実際の学習順序を示すStepを持たせる。これによりAIが作成した自然言語の計画を、アプリ側で進捗表示できる構造へ変換する。
Goal: 「曜日7語を日本語から中国語で答えられる」など、達成条件を持つ成果目標。
Milestone: 「基本語順を理解」「曜日7語を学習済み」「ランダム出題で80%以上正解」のような中間地点。
Step: 「基礎文法を説明→例文練習→単語7語を登録→翌日復習」のような推奨学習順序。
Activity: 実際に行った会話、クイズ、発音練習、作文など。Activityの結果がStepやGoalの進捗を更新する。
例: 「中国語の曜日を覚える」
Goal: 7曜日を見て意味を答え、曜日を聞かれて中国語で回答できる。
Step 1: 星期 + 数字という基本構造を理解する。
Step 2: 星期一〜星期日をLearningItemとして学習する。
Step 3: 日→中 / 中→日の両方向クイズを行う。
Step 4: 「今日は何曜日ですか？」を含む短い会話で利用する。
Completion Rule: 直近2回の確認で90%以上正解し、会話問題を1回成功する。

プランの「重点」は単一カテゴリではなく、複数のSkill Dimensionに対する重みとして保持する。これにより「今月は単語中心だが発音も少し行う」といった柔軟なプランを表現できる。

Skill Dimensionは拡張可能とし、言語固有項目（中国語の声調、英語の冠詞など）はタグまたはSub-skillとして追加する。
21.6 進捗の考え方
進捗率を単純な「完了Step数 / 総Step数」だけで算出すると、学習成果と乖離する。そのため、UIでは複数の指標を分けて表示する。

Mastery
対象LearningItemやSkillの習熟度。
Consistency
学習日数、連続学習、週あたりの実施率。
Focus Balance
計画した技能配分と実際の活動配分の差。
Confidence
自己評価とクイズ・作文・発音等の実績から得る参考値。
21.7 アプリ側の可視化
現在のActive Planとゴールをトップに表示する。
「ゴールまで約65%」のような全体進捗と、語彙・文法・発音など技能別の習熟状況を分けて表示する。
今日 / 今週の学習実績、連続学習日数、予定に対する実施率を表示する。
Milestoneをロードマップまたはチェックポイントとして表示し、「次に何をやるか」を明確にする。
AIとの会話で新しい学習項目が生まれた場合、それが現在のPlan/Goalのどこに寄与しているかを紐付けて表示する。
計画から外れた学習も禁止せず、「寄り道」として記録し、必要ならAIがPlanへ取り込む提案を行う。
21.8 動的な再計画
Learning Planは開始時に一度生成して固定するのではなく、学習結果に応じてAIと定期的に見直せるようにする。
予定より早く習得した場合、Stepをスキップまたは次のGoalを提案する。
同じ項目を繰り返し間違える場合、重点配分を変更したり補助Stepを追加する。
学習が数日空いた場合、未完了タスクを一度に積み上げず、再開しやすい軽量なStepを提案する。
ユーザーが「今日は発音だけやりたい」と言った場合、Plan自体を壊さず当日のSession Focusだけ変更できる。
大きく目的が変わる場合はPlan Versionを更新し、過去の計画と達成履歴を残す。
22. Session（その日の学習）
Planが数日〜数週間の短期目標を表すのに対し、Sessionは「今この会話で何をするか」を表す。PlanとSessionを分けることで、長期方向性を維持しつつ、その日の気分に合わせた学習が可能になる。
plan_id: 関連するLearning Plan
session_goal: 今日の到達点
focus: 今日重点的に扱うSkill
difficulty: easy / normal / challenge
planned_duration_minutes: 任意
agent: 利用したAI
completed_activities: 実施したActivity
session_summary: 終了時にAIが作成する学習要約
23. Plan関連AI Tool / API案
create_learning_plan: 対話結果から新しいプランを作成する。
get_active_plan: 現在のゴール、Milestone、次のStepを取得する。
update_learning_plan: ゴール、重点度、期限等を変更する。
propose_plan_revision: 実績から再計画案を作るためのデータを取得・保存する。
start_learning_session: 今日のFocusを決め、Sessionを開始する。
complete_learning_activity: クイズ・作文・会話等の結果を記録し、関連Goalの進捗を再計算する。
complete_learning_session: Session要約と実績を保存する。
get_plan_progress: Web UI / AI向けにProgress、Mastery、Consistency等を返す。
24. アーキテクチャへの反映
既存のLearning Domainを、項目単位の学習管理だけでなくGoal Orchestrationを含むドメインへ拡張する。
[ ChatGPT / Gemini / Other Agent ]                 |         Agent Integration Layer                 |         Learning Service API                 |    +------------+-------------+    |            |             | Plan / Goal  LearningItem  Review Engine    |            |             |    +------+-----+-------------+           |  Session / Activity / Progress           |       Persistence           |  Analytics / Visualization
LearningItemは「学んだ内容」、Plan/Goalは「何のために学ぶか」、Session/Activityは「どう学んだか」、ReviewEventは「どれだけ定着したか」を表す。この4つの観点を分離することで、AIエージェントを交換しても一貫した学習体験を維持できる。
25. MVPへの反映
Plan機能は本プロダクトの差別化につながるため、完全な適応学習アルゴリズムを待たずMVPにも最小形で含める価値がある。
1ユーザーにつき複数Planを保持し、1つをActiveにできる。
AIとの対話からGoal、Focus、3〜7個程度のStepを生成・保存できる。
各Stepをnot_started / in_progress / completedで管理できる。
LearningItemとStep / Goalを紐付けられる。
学習日とActivity件数から簡易Consistencyを表示する。
Web UIでActive Plan、次のStep、全体進捗、直近7日間の学習状況を確認できる。
Planの編集・中断・完了と、新Planへの切り替えができる。
26. この機能が生むプロダクト価値
この拡張によって、本サービスは「AI会話から単語を保存する外部単語帳」ではなく、「ユーザーとAIが一緒に学習方針を作り、複数のAIをまたいで進捗を継続できるLearning OS」に近づく。
ユーザーは毎回「今日は何を勉強すればいいか」をゼロから考えなくてよい。
AIは過去の目標と進捗を踏まえた会話を開始できる。
ChatGPTで会話練習、別AIで発音練習、自作アプリで復習しても、一つのPlanへ実績を集約できる。
学習項目単位では測りづらい「目標に近づいている感覚」をUIで提供できる。
将来的にはPlan Template、コミュニティ共有、教師作成Plan、AIによる自動最適化などへ展開できる。
27. 商用化・一般公開に向けた差別化課題
本サービスを商用化・一般公開する際の重要な懸念として、ChatGPTやGeminiなどのAIエージェント単体でも、会話履歴やメモリ等を利用することで、学習者が過去に学んだ内容をある程度保持し、継続的な語学学習を支援できる点がある。したがって、「AIとの会話内容を保存する」「覚えた単語を記録する」だけでは、外部サービスを導入する十分な理由にならない可能性がある。
27.1 プロダクトとして解決すべき問い
設計・開発では常に「AIエージェント単体では解決しにくい、あるいは安定して提供しにくい学習課題は何か」を基準に価値を検討する。AIエージェントの機能向上によって容易に代替される機能ではなく、複数AIをまたいだ継続性、構造化された学習計画、客観的な進捗測定、復習スケジューリング、学習履歴の長期蓄積・分析など、専用サービスだからこそ提供しやすい価値を中心とする。
27.2 AI単体との差別化候補
AI非依存の学習データ基盤：ChatGPT、Geminiなど利用するAIが変わっても、学習履歴・習熟度・プランを継続できる。
構造化されたゴール管理：曖昧な会話上の目標ではなく、Goal / Milestone / Stepとして進捗を測定できる。
長期的な習熟度モデル：単に「以前この単語を話した」ではなく、正答率、忘却、復習間隔、技能別の習熟度を蓄積する。
学習行動の可視化：ゴール到達度、継続日数、学習時間、技能バランス、弱点などをダッシュボードとして確認できる。
計画と実績の比較・再計画：当初の重点配分と実際の学習内容の差を検出し、AIと相談してプランを調整できる。
複数エージェント間のポータビリティ：特定AIのメモリ仕様や会話履歴にロックインされず、同じ学習コンテキストを別のAIへ渡せる。
27.3 設計原則への追加
本サービスは「AIエージェントに不足している記憶を補うツール」だけを目指さない。AIエージェントが今後さらに高性能になり、長期記憶や学習支援機能が強化されることを前提に、それでも独立して価値が残る学習管理・測定・可視化・データポータビリティの基盤を目指す。機能追加時には、その機能がAI単体との差別化に寄与するかを評価する。
28. AIエージェントの特性を活かす機能設計
本サービスはAIエージェントの不足を補うだけでなく、人間の講師・書籍・従来型学習アプリとは異なるAIの長所を増幅し、短所は専用アプリ側で補完する。AIとアプリを競合させず、「対話・説明・生成・適応はAI」「高速反復・保存・測定・検索・オフライン利用・専用入出力はアプリ」という役割分担を基本とする。
28.1 間隔反復と忘却管理
LearningItemごとに最終学習日、正答履歴、想起難度、次回復習候補日を保持する。AIとの会話中に復習対象を自然に再登場させる方法と、アプリ上で高速に一問一答する方法を併用する。
28.2 弱点マップと細粒度スキルモデル
語彙・文法・発音・作文などの大分類だけでなく、疑問文、時制、曜日、数字、買い物表現など細粒度のSkillを定義し、習熟度を可視化する。PlanのGoal / Milestoneと接続し、次に何を学ぶべきかをAIが判断できる材料とする。
28.3 「知っている」と「使える」の分離
LearningItemの状態を seen / recognized / recalled / produced / mastered のような段階で扱う。意味を見て理解できること、日本語から想起できること、会話中に自発的に使用できることを別の能力として記録する。
28.4 偶発学習とPersonal Phrasebook
AIとの自然な会話中にユーザーが質問した語句・文法・言いたかった文章を自動的に学習候補として回収する。教材起点ではなく「自分が実際に言いたかったこと」から個人教材が成長する。例文単位でも保存し、後日、日本語から英語・中国語へ再現する問題として再利用する。
28.5 AIによる自動学習ログ
明示的な学習開始操作を必須とせず、AIとの対話から新規学習項目、自力で使えた項目、誤答、ヒント使用、学習テーマ等を構造化してActivity / ReviewEventとして記録する。記録作業そのものを学習者へ要求しないことを価値とする。
28.6 Teacher Context API とAI間の引き継ぎ
AIには単語一覧だけでなく、現在のGoal、Level、Step、弱点、復習期限、直近の誤答、今日のSession希望などをまとめたLearning Contextを提供する。ChatGPTからGemini等へ移動しても、教師が交代しただけで授業が続く体験を目指す。
28.7 実生活ミッションとゴール逆算
「曜日を全部言える」「旅行先でホテルチェックインできる」「60秒の自己紹介ができる」など実技ベースのMissionを作成する。期限や利用場面から必要SkillをAIが逆算し、学習ロードマップと模擬試験を生成する。
28.8 AI評価の信頼度
AIによる習熟判定は確定事実として扱わず、masteryとconfidenceを分離する。同じ能力を異なる文脈・日時・出題形式で再確認し、観測数が増えるほど評価の信頼度を上げる。
29. 学習手段ごとの長所・短所を組み合わせる設計
単にAIチャットを便利にするのではなく、AI会話、書籍、単語帳、人間講師、従来型学習アプリそれぞれの長所を取り込み、弱点を相互補完する。
29.1 AIだからこそ強化できる体験
AIには「同じことを何度聞いても心理的負担が小さい」「説明方法を何度でも変えられる」「ユーザー固有の例文を即座に生成できる」「時間や場所を選ばず質問できる」「正解だけでなく、なぜ間違えたかを対話で掘り下げられる」といった強みがある。これらを学習データとして活用する。
例えば同一概念への再質問回数は単なる失敗ではなく、「人間相手なら聞き返しにくかった内容をAIだから繰り返し確認できた」という価値指標になり得る。再質問回数、説明変更回数、ヒント要求回数などを本人向け分析に利用し、「自分はどの説明で理解しやすいか」という学習スタイルの発見につなげる。
29.2 高速反復はアプリ側で補完
AIとのターン制対話には一定の応答待ちがあり、数十語をテンポよく一問一答する用途では専用UIの方が適する。単語カード、選択問題、タイピング、スワイプ判定、赤シート風表示などはローカル処理中心で即応させ、解説が必要になった瞬間だけAIへ遷移できる設計とする。
29.3 オフライン・低通信環境での復習
書籍や紙の単語帳の「通信不要ですぐ開ける」という利点を取り込む。直近のLearningItem、今日の復習セット、例文、Plan概要等を端末へキャッシュし、電波が悪い場所でも閲覧・簡易クイズを可能にする。オンライン復帰後に学習履歴を同期する。
29.4 検索・整理・しおり
AIとの会話は情報が時系列に流れやすいため、学習内容をLanguage / Skill / Topic / Plan / 日付 / 習熟状態で横断検索できるようにする。お気に入り、しおり、後で復習、重要マーク、タグ、学習ノート等を提供し、書籍の付箋やしおりの利便性をデジタルで拡張する。
29.5 赤シート・隠す学習のデジタル化
意味、訳、読み、例文の一部など任意のフィールドを隠して想起させる。紙の赤シートの即時性を維持しつつ、隠す対象を学習状況に応じて自動変更する。
30. AIチャットの制約を前提とした専用機能
AIエージェントは万能な学習UIではない。対話モデル・端末・音声認識・ネットワーク等の制約を明示的に設計へ織り込み、適切な処理を専用アプリへ逃がす。
30.1 音声・発音評価の独立レイヤー
音声入力が文字起こしを介する場合、AIが実際の発音音声そのものを十分に評価できないケースがある。将来的には録音音声を扱えるSpeech Adapterを独立させ、音素・アクセント・流暢さ・イントネーション等の評価を専門サービスまたは専用モデルで行い、その結果だけをLearning Contextへ統合できる構造とする。特定AIの音声機能へ依存しない。
30.2 入力手段を学習目的に合わせる
モバイル/PCキーボードによる入力は便利だが、予測変換・自動修正・IMEが学習結果へ影響する。自由入力、文字並べ替え、手書き、選択式、音声、ディクテーション等をActivityごとに選択し、「入力補助ありで正解」と「完全想起」を区別して記録する。
30.3 レイテンシを隠すハイブリッドUX
AI応答を待つ必要がない問題は端末内で即時判定し、AI生成が必要な解説・会話・問題生成は非同期的に先読み・キャッシュする。Session開始時にAIが10問程度をまとめて生成し、その後はローカルで高速出題する方式も候補とする。
31. AIネイティブならではの追加アイデア
31.1 Explanation Memory（効いた説明の記録）
同じ概念について複数の説明を試した際、どの説明・例え・言語・例文で理解できたかを記録する。次回は「以前この説明で理解しやすかった」という情報をAIへ渡し、ユーザー固有の教え方そのものを学習する。
31.2 Misconception Graph（誤解の構造化）
誤答を単純な×として扱わず、「AとBを混同している」「語順規則を逆に覚えている」など誤解の原因をAIが仮説化する。同じ原因から派生するミスをまとめて提示し、根本的な修正を促す。
31.3 Challenge Dial（その日の負荷調整）
Session開始時や途中で「軽く復習」「普通」「今日は攻める」など負荷を調整できる。正答率、反応時間、ヒント利用、直近の学習量からAIが難易度を動的に調整し、Planを壊さずその日の気分に合わせる。
31.4 Evidence-based Progress（進捗の根拠表示）
「あなたは70%習得」のようなブラックボックス表示ではなく、「過去7日で5回自力使用」「異なる3文脈で正解」「2週間後の再テストでも正解」など、進捗判定の根拠をユーザーが確認できるようにする。AI評価への過信を防ぎ、達成感も高める。
31.5 Learning Data Export / Ownership
学習者自身がLearningItem、履歴、Plan、Skill評価をCSV/JSON等で持ち出せるようにする。特定AI・特定サービスへのロックインを避けること自体をプロダクト価値とし、将来的な他AI・人間講師・他学習サービスへの引き継ぎを容易にする。
32. 将来的な他学習分野への展開
初期ターゲットは語学に絞る。語学は単語・文法・発音・作文・会話など学ぶ対象を分類しやすく、Skill、LearningItem、ReviewEvent、Goalの雛形を作りやすいため、学習基盤の検証領域として適している。
一方、Learning Plan、Goal / Milestone / Step、LearningItem、ReviewEvent、Mastery / Confidence、弱点分析、間隔反復、AIによる説明・問題生成という中核概念は、音楽理論、歴史、数学、プログラミング、資格試験などにも応用可能である。将来的にはLanguage固有のSkill Schemaを差し替え可能なDomain Moduleとして切り出し、汎用的な「AI連携型Learning OS」へ発展できる余地を残す。ただしMVP段階では汎用化を先行させず、語学で価値を実証してから抽象化する。
33. 導入容易性・AI起点オンボーディング
本サービスの重要な非機能要件として、ChatGPTやGemini等をモバイルアプリ・Web版で日常的に利用しているユーザーが、専門知識や複雑な設定なしで導入できることを置く。サービスの価値を理解していても、MCP、APIキー、OAuth、拡張機能等の設定が障壁になれば一般ユーザーへの普及は難しいため、「導入時の認知負荷を最小化すること」自体をプロダクト機能として設計する。
33.1 理想オンボーディング
理想的な体験は、ユーザーがAIエージェントに「（本サービス名）を導入して」「この学習を（本サービス名）で管理したい」と自然言語で伝えるだけで、AI側が利用可能な連携手段を検出し、インストール・接続・認証へ案内し、そのまま初期設定まで完了できる状態である。対応プラットフォームで自動インストールやワンクリック接続が提供される場合は積極的に利用し、ユーザーにMCPやAPIといった技術用語を意識させない。
33.2 プラットフォーム差異を吸収する接続レイヤー
ChatGPT、Gemini、将来の他AIでは外部サービス連携の方式や権限モデルが異なる可能性が高い。アプリ本体から接続方式を分離し、Agent Connector / Adapterとして実装する。ユーザー体験としては同じ「接続する」操作に見せつつ、内部ではMCP、公式連携機構、OAuth、Deep Link、Web経由の認証等、その時点で各プラットフォームが許容する最小手順を選択する。
33.3 導入レベルの目標
オンボーディングは段階的に評価する。最上位目標は「AIへの一言で導入開始」、次点は「AIが提示した1リンクを開いて承認するだけ」、それが不可能な環境でも「アプリ側でログイン後、利用AIを選択して数ステップで接続」までに抑える。APIキーの手動コピー、設定ファイル編集、コマンド実行などは一般ユーザー向けフローから排除する。
33.4 初回接続直後の価値提示
接続後すぐに空のダッシュボードを見せない。可能であればAIとの直近の学習文脈から、現在学習している言語、学習候補の単語・表現、推定レベル、短期Goal候補を生成し、「すでに使える状態」から開始する。履歴参照ができない場合も、AIとの短い対話で初期Learning Planを作成し、その結果をアプリへ自動反映する。
33.5 AI側とアプリ側の双方向導線
導入後は、AIからアプリを開く導線と、アプリから普段使うAIへ戻る導線を双方に用意する。例として「今日の復習をアプリで開く」「この弱点についてChatGPTに相談する」「このPlanをGeminiで続ける」など、利用者がサービス境界を意識せず往復できるUXを目指す。
33.6 未対応環境へのフォールバック
すべてのAI・端末・アカウント種別で同一の自動導入体験が実現できるとは限らないため、設計上は能力検出とフォールバックを前提とする。自動接続が使えない場合でも、共有リンク、QRコード、ブラウザログイン、コピー可能な短い接続コード等へ段階的に切り替え、学習データ自体は同じアカウントへ集約する。
33.7 導入容易性を測るKPI
一般公開時はオンボーディング完了率、接続開始から初回LearningItem保存までの離脱率、必要操作数、初回価値到達までのステップ数、AIごとの接続成功率等を計測する。機能追加だけでなく、「使い始めるまでの摩擦」を継続的に削減することをプロダクト改善の主要テーマとする。
33.8 設計原則
本サービスは「AI連携に詳しいユーザーだけが使えるツール」にしない。AIエージェントを普段使っている一般ユーザーが、技術的な接続方式を理解しなくても利用できることを前提とする。また、理想UXとしての「AIに導入を頼むだけ」を掲げつつ、実装可否は各AIプラットフォームが提供する公式連携・インストール・認証機能に従い、特定ベンダーの非公開挙動には依存しない。
34. プロダクト設計原則 - 既存学習体験から得た反面教師
既存の学習アプリやAI学習を単純に否定するのではなく、反復・習慣化・体系的カリキュラム等には合理性があることを認めた上で、固定化・強制・画一化による摩擦をAIの柔軟性で取り除く。万人向けに設定項目を増やしすぎず、必要な個人差は対話と学習履歴から徐々に推定する。
34.1 成果を中心に評価し、習慣は手段として扱う
連続学習日数だけを成功指標にせず、一定期間で何を習得し、何ができるようになったかを上位の評価軸とする。一方、継続を軸にした方が学びやすい利用者もいるため、習慣化を否定しない。PersonalizedはEverything is configurableを意味しない。
34.2 反復を残しつつ、不要な反復を診断で減らす
簡単な項目を即座にスキップするのではなく、短い診断問題等で定着を確認してから優先度を下げる。反復練習の価値を残しながら、既に十分習得した内容への時間消費を減らす。
34.3 カリキュラムはAIと相談して編集可能にする
ユーザーが使わないと感じる領域は優先度を下げられる一方、AIは一般的な使用頻度やGoalとの関連性から『実は実用的』な項目を理由付きで提案できる。最終的には利用者が選択する。
35. Teacher's Chart（学習カルテ）
学習者が何を知っているかだけでなく、『この人にはどう教えると学びやすいか』を蓄積するTeacher's Chartを中核概念として追加する。AI教師自身が利用者との学習を通じて教え方を学ぶ。
カルテ候補には、理解しやすかった説明形式、説明の好みの長さ、褒め方、訂正頻度、確認問題をしつこいと感じる傾向、ヒントの出し方、テンポ、話題転換の好み、語源・由来・面白い小話が記憶に効いたか等を含める。大量の設定画面をユーザーに要求せず、必要に応じてAIが提案し本人が修正できる。
35.1 Teaching Strategyの適応
同じ項目で停滞した場合、単純に出題回数を増やすだけでなく、教え方を変更する。語源、語呂、対比、本人の生活を使った例文、面白い由来、別形式の問題等を試す。疲労や停滞が見られる場合は一旦スキップし、数日〜数週間後の『リベンジ』として再スケジュールする。
35.2 Teaching Personality
教師の振る舞いも個人最適化する。例としてEnergetic Tutor、Calm Teacher、Casual Friend、Strict Coach等を想定し、pace / praise / correction_frequency / explanation_depth / initiative / topic_transition等のパラメータへ落とす。実在キャラクターの無許諾模倣を前提とせず、オリジナル人格や適法なコラボを想定する。
35.3 Conversation Momentum
AIが前の話題を広げすぎて次へ進みにくい、逆に返答が完結して学習意欲が途切れる、といった会話上の摩擦を扱う。短時間Session中は必要に応じて『回答→最小限の説明→次の問い』を維持する一方、話題転換は妨げない。未完了の学習状態は保持し、後から自然に戻れるようにする。
36. Personal Language Profile - 本人の言語生活を教材化
趣味や職業を例文へ入れるだけでなく、本人が母国語で日常的に何を話し、どのような表現を頻繁に使うかを教材へ変換する。口癖、頻出テーマ、よく使う文型、日常場面、『母国語ではよく言うが学習言語では言えない』表現等をPersonal Language Profileとして徐々に形成する。
一例として、最初に母国語で数分間たわいない雑談を行い、そこから学習言語では表現が難しそうな本人らしいフレーズを抽出し、翻訳・英作文・会話練習へ利用する。教材のパーソナライズではなく『その人の言語生活そのものを教材化する』ことを目指す。
37. AI学習特有の制御
37.1 AIの親切さを学習目的に合わせて抑制する
通常のAIは質問への答えを提供することが価値だが、学習時には即答が想起を妨げることがある。Learning Goal、習熟度、過去のヒント履歴、Teacher's Chartを参照し、待つ、最小ヒント、追加ヒント、答え提示の順を使い分ける。
37.2 誤答の種類に応じてテンポを変える
タイプミスや単純なSlipで長い解説を行わず、Unsure / Misunderstanding / Unknown等を推定して介入量を変える。本質的な誤解が続く場合だけTeaching Strategyを変更する。
37.3 評価と励ましを分離する
褒められることを好む利用者には積極的に励ますことができるが、励ましと能力評価は混同しない。Teacher/Tutorとしての会話体験とAssessmentとしての厳密な評価基準を分離する。
37.4 訂正の重要度をGoalとContextで決める
すべてのミスを等しく訂正しない。旅行・友人との日常会話・ビジネス等のGoalに応じ、意味伝達に致命的か、自然さの問題か、フォーマルさの問題かを考慮して介入頻度を変える。Correctness / Naturalness / Register / Appropriatenessを別軸として扱う。
38. AI教材の信頼性と検証
ChatGPTやGemini等は誤る可能性があるため、AI出力を無条件に正解データへ昇格させない。学習者のmastery/confidenceとは別に、教材情報自体のreliability/provenanceを保持する。AI Generated / Cross Checked / Source Verified等の状態を候補とする。特に『ネイティブはこう言う』『最近のスラング』等の変化しやすい情報は慎重に扱う。
38.1 Naturalness PoC
初期検証として、AIが初心者へ提示した表現群をネイティブ話者に評価してもらい、自然、意味は通るが不自然、教科書的、場面依存、あまり使わない、誤り等に分類するPoCを行う。複数AI間でも比較し、Verification Layerの必要度を実測する。
39. 10分程度の短時間学習へのフォーカス
初期プロダクトは『1時間みっちり学ぶ』体験へ無理に適応せず、10分前後で気軽に学べることを主要な価値とする。長時間学習を禁止するものではないが、MVPでは短時間で知識を取り込み、復習し、少し実践できる体験へ集中する。
39.1 得意領域と不得意領域を明示する
初期段階では、単語・表現・文法等の知識習得、英作文・翻訳・想起練習、短い対話練習を主要領域とする。長時間集中学習、手書き能力、精密な発音採点、実際の人間とのリアルタイム会話能力を完全に代替することは目標にしない。AIやスマートフォンが不得意な領域をすべて自作機能で解決しようとしてプロダクト規模を肥大化させない。
40. スピーキング・英作文・翻訳
精密な発音採点には限界があっても、『自分が言いたい内容を学習言語で自力で産出できる』ことは対象に含める。端末のマイク入力、文字入力、AI評価、本人の自己チェックを組み合わせる。
40.1 Speaking Activity
出題に対してマイクで回答し、文字起こしされた内容をAIが文法・意味・自然さ等から評価する。併せて本人が『止まらず言えたか』『言い直したか』『文字を見たか』『入力後に手修正したか』等を簡単に自己申告できるようにする。試験ではなく本人の学習支援であるため、自己申告を有効なEvidenceとして利用する。
40.2 自己評価とAI評価の差を学習データにする
AI評価は良好だが本人は詰まったと感じた場合は、知識はあるが瞬発的な産出が弱い可能性がある。逆に本人は流暢と感じてもAIが複数の文法ミスを検出した場合は、流暢さと正確性のギャップとして扱う。
40.3 発音評価の段階設計
Level 1: 本人による自己評価。Level 2: 音声認識が狙った内容を認識できたかという間接Evidence。Level 3: 将来的なSpeech Adapter等による音素・声調・アクセント・イントネーション評価。Level 2を『発音が正しい証明』とは扱わない。
40.4 英作文・翻訳の入力モード
Typing / Speaking / Assist等のモードを用意し、自力完成、言い直し、ヒント利用、答え参照、IMEや自動修正の利用等を区別して記録する。正解という一値ではなく、どの程度自力でProducedできたかを評価する。
41. 自由なAI人格と集約型Learning OS
学習データの集約先は本サービスだが、経由するAIエージェントはTutor / Friend / Roleplay / Examiner等の自由な姿を取れる。Friendとして雑談した内容からもLearning Eventを抽出できる。特定チャットセッションそのものを学習環境として固定せず、学習状態を外部基盤へ保持することでAIの自由度を活かす。
42. AI利用行動のリサーチ課題
一般ユーザーがChatGPT/Geminiをいつ、どの端末で、何のために開くかを調査する。仕事の調査、レシピ、恋愛相談、愚痴、検索等の日常利用から『ついでに10分学習する』導線が存在するのか、あるいは『勉強したいからAIを開く』方が自然なのかを検証する。結果に応じてAI起点・自作アプリ起点の比重を決める。
43. 商用化・課金に関する現時点の原則候補
継続契約そのものを学習継続の動機にしたり、ユーザーが蓄積したLearning Dataを閲覧し続けるために課金を要求したりするモデルは避けたい。学習者自身が蓄積した情報は本人の資産として扱う。
収益モデルは未決定とし、任意の支援・チップ型、価値を感じた機能への課金、B2B中心等も含めて後続検討する。直接課金を弱める思想にはAI生成教材の不確実性への責任感も背景にある。一方、料金を払って確実な実績・体系的カリキュラムを求める市場も存在するため、思想だけで決めず事業性を検証する。
44. 現時点のプロダクト仮説
本サービスの初期仮説は『AIとの約10分の学習を、本人に合った教え方で実施し、その場限りの会話にせず、長期的な習得へ変換する学習基盤』である。AIは対話・説明・生成・柔軟な人格を担い、サービスはPlan、Teacher's Chart、LearningItem、Evidence、復習、信頼性、検索、可視化、AI間の継続性を担う。
